Section 1

Why an operating system?

Problem

Without an OS, every piece of software would have to be written for each kind of device.

The OS abstracts access to computer resources. It has three roles:

HideHardware complexity

Programs use simple abstractions (files, processes…) instead of raw hardware.

ManageHardware resources

Share CPU, memory and devices between programs.

ProtectIsolation and protection

A program cannot break another one, or the system.

Watch out

The definition of an operating system is not exact.

A broad spectrum of OSes, depending on usage

Embedded systemssmall & optimized · ≤ megabytes
Graphical OSes, lots of featuresbig & feature-rich · ≥ gigabytes
Section 2

CPU and privilege

The x86 CPU provides security mechanisms through privilege rings.

ModeRingRights
Kernel mode0Everything is allowed
User mode (userland)3Restricted instructions and memory space
Key point

Privilege is a mechanism provided by the CPU (hardware), not by software.

Each CPU architecture has its own security mechanism:

  • x86: rings 0 to 3
  • ARM: supervisor mode and user mode
Section 3

What is a kernel?

Definition

The kernel is the program running in ring 0.

  • It is the main part of the operating system.
  • It is the most privileged program, and therefore the most critical.
  • If it fails, the whole computer fails.

Kernel roles: what this course covers

Section 4

Kernel types

The question

What runs in ring 0, and what runs in userland?

4.1 Monolithic kernel ex: old Unix

The whole OS runs in kernel space, as one single big program. Drivers, memory management, scheduler, filesystems, network stack: everything is compiled together into one binary running in ring 0.

Userland
AppAppApp
Ring 0
ONE SINGLE BINARY
SchedulerMemoryFilesystemsNetworkIPCDevice drivers
Pros
  • Fast: components call each other directly (simple function calls)
  • Simple design
Cons
  • Huge codebase running with full privileges
  • A bug in any part (e.g. a driver) can crash the whole system
  • Adding a driver means recompiling the kernel and rebooting

4.2 Modular (monolithic) kernel ex: Linux

A monolithic kernel that can load and unload pieces of code (modules) at runtime. It is still monolithic: modules run in ring 0, inside the kernel's address space. But you don't need to recompile or reboot to add a driver.

Ring 0

rmmod <module>     # unload a module
Pros
  • Keeps the speed of a monolithic kernel
  • Flexible: load only the drivers you need
  • Smaller kernel in memory
Cons
  • A buggy module still runs in ring 0, so it can still crash everything

4.3 Microkernel ex: Minix, QNX, seL4

Only the bare minimum runs in ring 0 (scheduling, basic memory, IPC). Everything else (drivers, filesystems, network) runs as servers in userland. Seen here mainly to understand hybrid kernels.

  • Slower: lots of messages and context switches between userland and kernel

4.4 Hybrid kernel ex: Windows NT ex: macOS XNU

A compromise between monolithic and microkernel: designed like a microkernel (separated components), but most services are kept in ring 0 for performance.

Interrupt handler

When an interrupt or an exception occurs:

  • the userland program running is paused;
  • the kernel runs the corresponding handler in kernel mode.

Timer interrupt EXAMPLE OF HARDWARE INTERRUPT

The Programmable Interval Timer (PIT):

  • is a chip that can set its outputs at a programmed frequency;
  • is connected to some I/O ports of the CPU;
  • at each PIT tick, the CPU is interrupted and jumps to the interrupt handler.

Trap instruction

Definition

A trap is an assembly instruction that raises a software exception.

A trap can be put in a userland program to interact with a debugger or with the kernel. Different kinds of trap instructions:

→ debugger Breakpoint instruction

Used for debugging: execution stops and the debugger takes over.

int3on x86 (opcode 0xCC)
→ kernel Force a kernel-mode switch

Used for system calls: the program asks the kernel to do something for it.

syscallx86-64int 0x8032-bit Linux

The second kind is how system calls work: see §6.

Section 6

System calls

Definition

Syscalls are the entry points to the kernel from the userland.

  • A userland process asks the kernel to perform a privileged action.
  • From the userland point of view, calling a syscall is like calling a function.
  • The program executes a trap instruction, which raises an interruption.

The full sequence, step by step, is at the end of this section.

Same mechanism as interrupts

The mechanism behind syscalls is similar to interrupt handling. The difference: for a syscall, it is the user process itself that fires the interruption. It traps itself.

Trap instructions are CPU-specific

ArchitectureTrap instructionNote
i386 (x86, 32-bit)int $0x80backward compatible, see below
x86-64syscalldedicated, faster instruction
ARMswi 0x0"software interrupt", now spelled svc #0
RISC-Vecall"environment call"

See man 2 syscall: it lists, for each architecture, the instruction and which registers hold the number, the arguments and the result.

filled in

Why is int $0x80 "backward compatible"?

  • On 32-bit x86, Linux syscalls go through software interrupt number 0x80 (128). The CPU looks up entry 0x80 in the interrupt table (IDT) and jumps to the kernel handler, exactly like a hardware interrupt.
  • x86-64 added the dedicated syscall instruction. It jumps straight to an address the kernel stored in a CPU register, skipping the interrupt-table lookup, so it is faster.
  • A 64-bit Linux kernel still accepts int $0x80 so that old 32-bit programs keep running unchanged. That is the backward compatibility.
  • Trap for the exam: int $0x80 always uses the 32-bit conventions. Numbers come from the 32-bit table (exit = 1, write = 4, not 60 and 1), arguments go in ebx, ecx, edx…, and only the low 32 bits of registers are read, so 64-bit pointers get truncated. In 64-bit code, use syscall.

How to call a syscall LINUX X86-64

  1. Put the syscall arguments in %rdi, %rsi, %rdx, %r10, %r8, %r9 (in that order, up to 6).
  2. Put the syscall number in %rax.
  3. Raise a trap interruption (syscall).
  4. The kernel performs the syscall, then returns.
  5. The return value is in %rax.
  6. Check errno.The raw syscall returns -errno (a value between −4095 and −1) on failure. The libc wrapper turns that into a return value of -1 and stores the error code in the global errno, so in C you test if (ret == -1) perror("…");
raxnumber → result
rdiarg 1
rsiarg 2
rdxarg 3
r10arg 4
r8arg 5
r9arg 6

filled in Arg 4 goes in r10 and not rcx because the syscall instruction overwrites rcx (return address) and r11 (flags).

; write(1, msg, 14): print "Hello, world!\n"
mov rax, 1       ; syscall number: write
mov rdi, 1       ; arg 1: fd 1 = stdout
lea rsi, [msg]   ; arg 2: address of the buffer
mov rdx, 14      ; arg 3: number of bytes
syscall          ; trap → ring 0
; rax = bytes written, or -errno on failure

How the kernel processes syscalls

Linux

  1. Trap instruction
  2. Jump to the kernel trap handlerentry point entry_SYSCALL_64
  3. Save the registers
  4. System call tablearch/x86/entry/syscalls/syscall_64.tbl
  5. Call the right entry (e.g. sys_read())
  6. Restore registers
  7. Return (iret)after int $0x80; after syscall the fast path returns with sysret

Windows filled in

  1. The app calls a Win32 functione.g. ReadFile() in kernel32.dll
  2. It calls the native stub NtReadFile() in ntdll.dll
  3. The stub puts the service number in eax and runs syscall
  4. Kernel trap handler KiSystemCall64 (in ntoskrnl.exe) saves the registers
  5. Looks up the SSDT (System Service Descriptor Table) with that number
  6. Calls the kernel NtReadFile(), then restores registers
  7. Returns to user mode (sysret)
Main difference filled in

Linux syscall numbers are stable: a program may use them directly. Windows syscall numbers change between versions and are not documented: programs must go through ntdll.dll / the Win32 API.

A syscall from start to finish filled in

Everything above, in order, for one real call on Linux x86-64: n = read(3, buf, 100); reads up to 100 bytes from file descriptor 3 into buf.

  1. Userland · your program
    The program calls read() like any C function

    It is an ordinary function call into the C library (glibc). The function-call ABI places the arguments in registers.

    rdi = 3 · rsi = buf · rdx = 100
  2. Userland · libc wrapper
    The wrapper prepares the syscall

    It puts the syscall number in rax: read is number 0 in the table. The arguments are already in the right registers (a 4th argument would be moved from rcx to r10).

    rax = 0 · rdi = 3 · rsi = buf · rdx = 100
  3. Userland · libc wrapper
    It executes the trap instruction syscall

    The process traps itself. From here, the program is paused.

  4. ring 3 → ring 0
  5. CPU · hardware
    The CPU switches to kernel mode and jumps to the kernel

    In a single instruction, the CPU saves the return address in rcx and the flags in r11, switches to ring 0, and jumps to the kernel entry point. The kernel registered that address in a CPU register at boot, so the program cannot choose where it lands.

    ring 0 · rcx = return address · r11 = flags
  6. Kernel · trap handler
    Switch to the kernel stack and save the registers

    entry_SYSCALL_64 stops using the user stack (the kernel doesn't trust it) and saves all the program's registers on its own stack, so the program can later resume exactly where it stopped.

  7. Kernel · trap handler
    Look up the syscall table

    The kernel checks that the number in rax exists (otherwise the result is -ENOSYS), then finds entry 0 in the table: sys_read.

    table[0] → sys_read
  8. Kernel · sys_read
    Do the real work, with full privileges

    It looks up fd 3 in the process's fd table, checks that buf really belongs to the process, reads the file and copies the bytes into buf. If no data is available yet (e.g. a keyboard), the process is put to sleep and the CPU runs other processes in the meantime.

  9. Kernel · trap handler
    Put the result in rax and restore the registers

    The result is the number of bytes read, or a negative error code such as -EBADF (bad file descriptor). The saved registers are restored and the kernel switches back to the user stack.

    rax = 42 (bytes read) or −9 (−EBADF)
  10. ring 0 → ring 3
  11. CPU · hardware
    Return to user mode: sysret

    The CPU reloads the return address from rcx and the flags from r11 and goes back to ring 3. The program resumes on the instruction right after syscall. (Some cases use iret instead, the same return as after an interrupt.)

    ring 3
  12. Userland · libc wrapper
    The wrapper checks for errors

    If rax is between −4095 and −1, it stores the error in errno (here errno = EBADF) and returns -1. Otherwise it returns rax unchanged.

  13. Userland · your program
    read() returns, like a normal function

    n holds the number of bytes read, or -1 with errno set. The program never saw the switch to ring 0.

    n = 42, or n = −1 and errno = EBADF

When do you need to check the ABI? filled in

Rule of thumb

If you only write C and recompile everything together, the compiler handles the ABI for you. You need to check it as soon as you work at the binary level: assembly, raw syscalls, already-compiled code, another language, or another machine.

SituationWhat to check in the ABI
Writing assembly that calls a C function, or that C callsWhich registers hold the arguments and the result. Which registers you must save and restore (on System V x86-64: rbx, rbp, r12–r15). The stack must be 16-byte aligned at the call.
Making a syscall by hand in assemblyThe syscall convention, which differs from function calls (r10 instead of rcx), and the number for your architecture: write is 1 on x86-64, 4 on i386, 64 on ARM64 and RISC-V.
Reading arguments in a debugger (gdb) at a function breakpointWhere each argument is: at the start of read(fd, buf, n) on x86-64 Linux, fd is in rdi, buf in rsi, n in rdx.
Calling C from another language (Python ctypes, Rust extern "C"…)Both sides must agree on the calling convention, the size of types (int, long, pointers) and the layout of structs.
Updating a shared library (.so, .dll) without recompiling the programWhether the new version is ABI-compatible: same functions, same struct sizes and fields. If not, the program still compiles but crashes or misbehaves. A new major version in the file name (libfoo.so.1 → libfoo.so.2) signals a broken ABI.
Running a binary on another machineSame CPU architecture, same file format, same OS. An x86-64 Linux ELF won't run on ARM, nor on Windows (PE format, other syscalls).
Writing a Linux kernel moduleThe ABI towards userland is stable, but the kernel's internal interface is not: a module must be rebuilt for each kernel version.

Where to look

  • man 2 syscall: syscall instruction and registers for every architecture. man 2 syscalls: the list of syscalls.
  • The System V x86-64 psABI (Linux, macOS), Microsoft's x64 calling convention page (Windows), AAPCS64 (ARM64), the RISC-V psABI.
  • Inspect a binary from the terminal:
file ./prog          # format, architecture, ABI: "ELF 64-bit LSB executable, x86-64, (SYSV)…"
readelf -h ./prog   # ELF header: class, machine, OS/ABI
ldd ./prog          # shared libraries it needs, with their version
objdump -d ./prog   # disassembly: see the registers actually used
Section 8

Standards: POSIX

filled in

POSIX = Portable Operating System Interface (the X is for Unix).

  • A standard by the IEEE (IEEE 1003.1, also ISO/IEC 9945), maintained with The Open Group.
  • It defines what a Unix-like OS must provide so that a program written for one system compiles and runs on another. It is an API standard (source level).
  • It covers the C interface (open, read, fork, pthread_create…), the shell and utilities (sh, ls, grep…), signals, environment variables and file paths.

Certified

A few OSes are certified, e.g. macOS from Leopard to Sequoia.

Almost conforming

A lot of OSes: Linux, OpenBSD, FreeBSD, Darwin…

Some programs make OSes conform, e.g. Cygwin for Windows.

You can check standard conformity in the man page section called STANDARDS. For example, man 2 read says POSIX.1-2008. Older man pages call this section CONFORMING TO.

Section 9

File descriptors

Definition

A file descriptor is an index in a file descriptor table. It represents an open file and is used in file operations.

// ignoring error checks
char buf[BUF_SIZE];
int fdin  = open("example_1.txt", O_RDONLY);
int fdout = open("example_2.txt", O_WRONLY);
ssize_t rn = read(fdin, buf, BUF_SIZE);  // up to BUF_SIZE bytes → buf, rn = bytes read
write(fdout, buf, rn);                     // write those rn bytes to example_2.txt
close(fdin);
close(fdout);

filled in Everything from read on is a reconstruction of the usual end of this example. open returns the smallest free index: here 3 and 4, because 0, 1, 2 are already taken.

File descriptor table

The table is part of the process data. Each process has its own table.

Universality of I/O

Unix philosophy on I/O

Everything is a file.

All things that have standard I/O operations are treated the same. They all use the same operations:

open(2)read(2)write(2)lseek(2)close(2)

The "seek" syscall is spelled lseek.

Regular fileexample_1.txt
Terminal/dev/tty
Disk/dev/sda
Black hole/dev/null
Kernel info/proc/cpuinfo
Pipe, socketfd from pipe(), socket()

So the copy program above works unchanged if example_1.txt is replaced by /dev/tty: it then copies the line you type into example_2.txt.

Recap

Key takeaways

  1. The OS sits between programs and hardware: it abstracts, manages and protects.
  2. The CPU enforces privilege levels: ring 0 = kernel, ring 3 = user.
  3. The kernel is the ring-0 program: most privileged, most critical.
  4. Kernel types: monolithic, modular (Linux), hybrid (Windows, macOS), microkernel. Each is a trade-off between speed and robustness.
  5. Exceptions/traps are synchronous and come from software; interrupts are asynchronous and come from hardware. In both cases the program is paused and the kernel runs a handler in kernel mode.
  6. A syscall is a program trapping itself on purpose: number in %rax, arguments in %rdi, %rsi, %rdx…, then syscall. The kernel looks up the syscall table and returns the result in %rax.
  7. API = source-level specification. ABI = binary-level specification (calling conventions, file formats). POSIX is the standard API of Unix-like systems.
  8. A file descriptor is an index in the process's own fd table. On Unix everything is a file, handled with open, read, write, lseek, close.
